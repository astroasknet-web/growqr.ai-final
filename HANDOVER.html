02 Admin access

Not an email allowlist. Admin status lives in Supabase.

Authorization is app_metadata.is_admin === true on the Supabase user. That field can only be written with the service role key, so users can never grant themselves access, and it rides in the session JWT so the check costs no round trip.

To add an admin: create the Supabase auth user, then set app_metadata: { is_admin: true } on them from the Supabase dashboard.

middleware.ts matches only /admin and /admin/:path*, and it fails open if the Supabase env vars are missing. Every /api/admin/* route therefore re-checks getAdminUser() itself and fails closed. Do not add an admin API route without that check.

Expert submissions have no admin page — check them manually. A person filling in /experts/submit posts to /api/expert-intake, and the row lands in the Supabase table public.expert_submissions with status = 'pending'. Their uploaded photo goes to the expert-media storage bucket, and the row's image_url points at it.

Where to look: Supabase dashboard → Table Editor → expert_submissions, newest first. Nothing in the product reads this table and no email is sent when a submission arrives, so it is unread until someone opens it. Approving one means copying the fields into experts-data.ts and deploying, since profiles are static (see above).

Booking flow

Availability is weekly rules expanded into slots by features/experts/services/slots.ts, minus Google free/busy and slots already taken. Booking creates a Google Calendar event with a Meet link, emails both sides, and queues 24h + 1h reminders at Resend.

Payments are wired but off. PAYMENTS_ENABLED = false in app/api/experts/book/route.ts. Bookings are free. All payment code and the invoice PDF templates are preserved — flip the flag to restore the pay-then-book flow.

2nd and 4th Saturdays are excluded as non-working days in slots.ts, in application code rather than in data. You will not find that in the availability table.

The Google account behind Meet links

The OAuth client lives in a Google Cloud console under sahil@growqr.ai. The stored token is for support@growqr.ai, and that token generates the Meet links and reads free/busy for every expert booking.

The token does not expire on its own, but it is not independently valid: authedClient() builds the client from GOOGLE_OAUTH_CLIENT_ID and GOOGLE_OAUTH_CLIENT_SECRET first, then attaches the refresh token, so every call re-authenticates against that Cloud project. If the project or its OAuth client is deleted, the token stops working immediately.

One shared connection, not one per expert. A single row with expert_slug = null. Completing the OAuth flow overwrites it, so whoever consents last owns every future Meet link. Losing it also stops internship interview scheduling.

To reconnect: set GOOGLE_CONNECT_ENABLED=true in Vercel, redeploy, sign in at /api/google/connect as an admin using support@growqr.ai, then unset it and redeploy. It stays unset in normal operation so the token cannot be overwritten by accident. /experts/connect is the branded success/failure page for that flow.

06 Internship Live · app APIs pending

Data home
Five tables: internship_applications, _interviews, _appointments, _emails, _settings.
To change
Fully from /admin/internship, including a settings page for the automation.
Breaks if
The interview service credentials are wrong, or a candidate's GrowQR account email does not match — see gotcha 3.
Not closed
Parts of the loop wait on APIs the app team has not shipped — see below.

The largest and most automated feature. Public entry is /growqr-internship and a four-step form at /growqr-internship/apply that prefills from the applicant's GrowQR profile link and uploads a resume.

Nine statuses, and a guard

new, screening, shortlisted, interview, selected, waitlist, offer, joined, rejected.

lib/internship/status-flow.ts defines a seven-step linear path. waitlist and rejected sit deliberately off it, and nextStatusOrNull() only ever moves forward. So automation can never move a candidate onto or off a human hold, and never backwards. Only a person can reject, waitlist, or mark joined.

Triage is not status

On submit, triageFor() bands the applicant auto_shortlist / on_hold / unscored against their RQ score (default threshold 50, configurable). It is written once and never recomputed, so changing the threshold later does not re-band existing applicants.

The AI interview

lib/internship/growqr-interview-api.ts talks to api.growqr.ai — the external interview service. An auto-shortlisted applicant is assigned a round on submit, if GROWQR_INTERVIEW_API_KEY and GROWQR_INTERVIEW_ORG_ID are both set. If they are not, the round is still created and tracked manually.

Results sync back three ways: the "Sync results" button, automatically whenever the detail page opens, and daily from /api/cron/crm-sync (which runs it before, and independent of, the CRM kill switch).

The service returns no hire/no-hire signal. Our verdict field is hr_verdict, named that way deliberately to avoid colliding with the service's candidate-coaching recommendations.

Auto-advance ships OFF. auto_advance_enabled defaults to false, so a passing score does not move anyone to Selected until someone switches it on in settings.

Final round and the appointment letter

Scheduling a final discussion creates a real Google Meet via the shared calendar connection, anchored to IST, falling back to a pasted link if no calendar is connected.

The appointment letter is a generated PDF (@react-pdf/renderer) attached to the email. Sending it stamps issued_at and advances status to offer. It deliberately contains no compensation figures — there is no such field anywhere in the table, form, or settings.

What is still pending from the app side

The website half of this pipeline is built and working. It is not a closed loop end to end, because several pieces depend on API surfaces the GrowQR app has not delivered yet. Worth knowing before anyone reports these as bugs on this repo.

Waiting onAlready built hereConsequence today
session_meta on the results payload Columns difficulty, duration_minutes, external_session_id exist (migration 0037) All three are never populated. Nothing writes them because the service does not return them.
GET /review/{session_id} The external_session_id column is stored separately for exactly this call No client function exists. There is no way to open a candidate's full interview review from admin.
A hire / no-hire signal hr_verdict field and its UI rendering The service returns only candidate coaching notes. Every verdict is entered by a human.
Assignment lifecycle endpoints unassign() and verifyPendingAssignment() are written and tested Zero callers. No way to cancel an assignment, and no delivery check — which is the guard against gotcha 3.

The client currently implements assignment creation, bulk results, the two account-email lookups, and a pending-assignment probe. Everything else in the schema was built ahead of the service.

The practical effect: a candidate can be assigned an AI interview and have a score sync back, and that much works. But nobody can cancel a mis-assigned interview, verify one was actually delivered, or read the full review — those need the app team first.

Settings

/admin/internship/settings writes a singleton row: RQ threshold, auto-assign on/off, AI round type per role, auto-advance and its pass score, default interviewer, calendar id, appointment-letter defaults, and four candidate-email toggles. getInternshipSettings() never throws — a missing row or a down database degrades to defaults rather than failing the request.

07 Ambassador Live · MVP

Data home
Two tables: ambassador_applications (the real form) and ambassador_waitlist (email capture when closed).
To change
APPLICATIONS_OPEN in components/pages/ambassadors/ambassadors-data.ts — a hardcoded constant, not an env var. Cohort name and seat counts are hardcoded there too.
Breaks if
Supabase env vars are missing — this feature fails open. See gotcha 1.

When APPLICATIONS_OPEN is true, /ambassadors/apply shows the real four-step form which posts to /api/send-ambassador. When false it shows a waitlist email capture posting to /api/ambassador-waitlist. Different form, different route, different table.

The form captures UTM parameters, where utm_medium holds the referring ambassador's id. Resume upload uses its own separate Turnstile token, because a token is single-use at verification.

Admin at /admin/ambassador: search and filter, change status, edit internal notes, manually add an application, delete, and export CSV. Statuses are pending, screening, interviewed, under_review, shortlisted, rejected.

The waitlist has no admin page — check it manually. While APPLICATIONS_OPEN is false, every email captured goes to the Supabase table public.ambassador_waitlist (three columns: id, email, created_at). Nothing reads it and nothing is sent when the cohort reopens.

Where to look: Supabase dashboard → Table Editor → ambassador_waitlist. Export it by hand when a new cohort opens, or those people never hear that applications are live again.

Two other things to know: applications never reach Zoho, and the CSV export contains aadhaar_number in plaintext alongside internal notes — treat that file accordingly.

These two routes are hand-rolled and do not use the shared form pipeline in section 08, which is why their failure posture differs.

Turnstile has no dev bypass, on purpose. An earlier version returned success when the secret was unset, which silently disabled bot protection on a misconfigured deploy. With no keys in .env.local the widget renders nothing, no token is produced, and every form returns 403.

Rate limiting is 5 requests per 10 minutes per form. It is an in-process map, not a shared store, so on serverless the real ceiling is higher than the number suggests. That is a documented trade-off, not a bug.

09 CRM sync Live

There is a proper runbook already: lib/crm/README.md. It is the most complete document in the repo. Read it before changing anything in lib/crm/. This section is only the orientation.

A submission reaches Zoho both immediately and nightly. The inline path fires within seconds of the response; the daily cron is the durability layer that catches anything a cold shutdown stranded. They cannot collide: claiming a row is a conditional update, the sweep ignores rows younger than ten minutes, and Zoho upserts on email so a double-fire cannot duplicate a lead.

Rows move pending → syncing → synced or failed, giving up after five attempts. A reaper resets rows stuck in syncing. A second lane retries rows that synced but whose follow-up work (a Zoho Task or Note) did not complete.

call_bookings is the only source that searches Contacts first. A converted lead becomes a Contact and disappears from the Leads search, so without that step a booking by an existing customer would create a duplicate.

List views in Zoho

Three custom views are load-bearing and should stay. Everything else was a one-off and has been cleared out — do not recreate that clutter.

ModuleViewWhy it stays
ContactsB2BMirrors the Segment value the sync writes
ContactsB2CSame, for the consumer side

Leads deliberately has no custom views — the system set covers it. If you add one, name it after something the pipeline actually writes (Segment, Lead_Source, Lead_Status), so it stays meaningful once the person who made it has gone.

Views cannot be deleted through the API. DELETE on /crm/v8/settings/custom_views/{id} returns INVALID_REQUEST_METHOD on every version, and it is not a scope problem. Read and edit work; removal is Zoho UI only, under Manage Views. A view marked default cannot be deleted until another view is made default.

Campaign segments are the ones that pile up. If you build a view for a single send, delete it once the send is done — but check no Zoho campaign still points at it first, because a campaign whose view is gone loses its recipient list.

Nothing in this repo ever creates a Deal. The B2C policy is enforced indirectly: the payload builder strips Company whenever the segment is B2C, and Zoho decides whether to create an Account purely from whether Company has a value. This depends on Company being non-required on the live Zoho Leads layout — a config dependency you cannot see from the code.

10 Chat bot & demo calls Live

SalesIQ bot

The widget mounts globally in app/layout.tsx. Answers come from bundled snapshots (lib/bot/kb-snapshot.json, faq-snapshot.json) with an OpenAI fallback. The webhook has a hard five-second budget, which is why the knowledge base is a bundled file rather than a live fetch, and why CRM writes happen after the response rather than inline.

Requests are authenticated by either an RSA signature verified against SALESIQ_PUBLIC_KEY, or a legacy shared-secret header. Either proof is sufficient.

Demo calls via Cal.com

Clicking a demo CTA fires an attribution beacon to /api/cal/intent, then opens Cal with source and intent as hidden booking questions. Cal echoes them back in the webhook, which is the only way page context survives the hop off-site.

The webhook is HMAC-verified, deduplicated by a hash of the raw body, and ordering-guarded. It returns 200 to anything durably recorded — only a bad signature (401) and an unavailable ledger (503) ask Cal to retry, because one malformed payload could otherwise become an endless retry loop.

Cal mints a new booking id on reschedule. Confirmed live. The RPC migrates the existing row onto the new id rather than inserting a duplicate, which would otherwise double-count the booking and create a second Zoho Task.

Guests on a booking (Kanika on B2B, Ruchi on B2C) are prefilled defaults the booker can delete, not enforced attendees. Real co-hosts need a Cal Teams plan, and collective scheduling would intersect calendars and shrink available slots.

11 Scheduled jobs

Two crons in vercel.json. Both require CRON_SECRET and refuse to run without it.

PathSchedule (UTC)What it actually does
/api/cron/crm-sync0 2 * * *Four jobs, in order: retry booking notifications, purge expired intents, sync interview results, then (only if enabled) drain the CRM queue and flush chat transcripts
/api/cron/expert-reminders30 2 * * *Top-up sweeper for the 24h + 1h session reminders

The first three jobs in crm-sync run before and independent of CRM_SYNC_ENABLED, so turning off CRM does not stop interview syncing or intent cleanup.

The reminder cron does not time delivery. Reminders are queued at Resend with a scheduledAt the moment a booking is created, which is why a once-daily run is enough. The cron only catches stages that failed to queue and bookings made beyond Resend's 30-day scheduling horizon.

Daily is a plan constraint, not a design choice — the Vercel Hobby plan caps crons at two, once per day. Nothing is lost by it; recovery is just slower.

14 Gotchas

Only what a new owner cannot simply fix. Everything else found during this handover has been fixed in the code.

Blocked on someone else

  1. The interview account-email trap. Assignments match the candidate's GrowQR account email, not the address on the application form. Get it wrong and the service returns success with a real assignment id, while the candidate never sees the interview. The guard against this — verifyPendingAssignment() — is written and tested but has no endpoint to call yet. Needs the app team.
  2. Zoho picklists accept invalid values silently. The API stores an unrecognised value instead of rejecting it, and Zoho matches on display names, so renaming a picklist in their UI breaks writes with no error anywhere. Not fixable from this side. Run npm run crm:drift before any picklist edit — that is the whole mitigation.
  3. Only two cron jobs, once a day. A Vercel plan limit, not a design choice. Normal operation is unaffected because the real work runs inline, but every recovery path inherits a day of latency: a stranded CRM row, a chat transcript waiting on its lead, and a failed 1-hour session reminder whose recovery window is 15 minutes and so is effectively never swept up. Fixing it means a paid plan or an external scheduler.
  4. Rate limiting is per-instance and in memory. On serverless the real ceiling is higher than the configured limit, because each cold start gets its own counter. Fine at current volume; solving it properly needs a shared store such as Redis.

Missing pieces someone has to build

  1. Recording an interview outcome by hand is API-only. The endpoints work and carry score, verdict, summary and reschedule, but nothing in the admin UI calls them. A human interview round cannot be scored from the dashboard.
  2. internship_emails is write-only. Every send is logged and nothing ever reads the table, so there is no timeline on the candidate and no "already sent" warning before a resend.

Things that are simply true, and will surprise you

  1. Local setup needs Turnstile keys or every form returns 403. There is deliberately no development bypass — an earlier version returned success when the secret was missing, which silently disabled bot protection on a misconfigured deploy. It looks like a broken form, not missing config.
  2. Bot answers come from a bundled snapshot, not a live fetch. Editing the SalesIQ Answer Hub changes nothing until someone runs npm run kb:export and deploys. Same for FAQs. Nothing warns you; the bot just keeps saying the old thing.
